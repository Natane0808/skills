## 方法 1：像素量测（用于布局问题）

### 为什么不能用肉眼
人眼能察觉"有点别扭"，但**说不出差多少**、也**判断不了是不是错觉**。
量测能在一秒内给出「左边 51px、右边 149px、差 98px」这种可行动的数字。

### 实现思路
沿水平扫描线，从左右两端向中间找"亮度突然变化"的位置（卡片边界），计算两侧留白。

```python
# 伪代码
def measure_edges(img, y):
    vals = [luminance(img, x, y) for x in range(width)]
    paper = (vals[8] + vals[width-9]) / 2      # 纸底亮度
    thr = paper + 2.5                          # 卡片比纸底亮一点
    left  = first x from 0 where vals[x] > thr
    right = first x from end where vals[x] > thr
    return left, width-1-right

# 判据
assert abs(left - (width-1-right)) <= 1   # 1px 是奇数宽度的取整容差
```

### 当时的发现
10 张截图**全部**是 `左 51 / 右 149`，一个像素都不差 —— 说明不是"某页写错"，而是**布局骨架的数学错误**。
如果是单页问题，各页数值会不一样。

### 关键启示
> **"全都一样"本身就是线索。** 它把排查方向从"找哪页写错了"切换到"找骨架哪里算错了"。

## 方法 2：A/B 对照（用于"这个因素是不是原因"）

### 适用场景
你有一个**假设**，比如"是不是参数顺序错了"。

### 做法
同时跑两组，只改**一个变量**，其余完全相同，用可量化的指标比对。

### 当时的发现
怀疑"`opacity` 写在 `animate` 之前/之后会影响动画"：

| 时刻 | A（先 opacity 后 animate） | B（先 animate 后 opacity） |
| --- | --- | --- |
| 初始 | 235 | 235 |
| +120ms | 221 | 219 |
| +300ms | 184 | 184 |

两条曲线几乎重合 → **顺序不是原因**，假设被排除。

### 关键启示
> **A/B 对照的价值在于"排除"**，不在于"确认"。
> 每排除一个假设，剩下的可能性就少一个。

---

## 方法 3：对照组（用于"这个功能到底支持不支持"）

### 适用场景
怀疑某个 API 不支持，但不确定。

### 做法
同一张截图里放**多组**：实验组 + 已知能工作的对照组 + 边界组。

### 当时的发现
怀疑 Canvas 渐变不支持：

| 组 | 写法 | 结果 |
| --- | --- | --- |
| E1 | 渐变 + beginPath + stroke | ✅ 沿弧有色差 |
| E3 | **纯色**（对照组） | ✅ 恒色（Δ0） |
| E5 | 渐变但端点退化 | ✅ 但恒色（Δ0） |

**判别逻辑**：同一张图里 E1 在变、E3/E5 不变 → 变化来自渐变而非渲染误差 → **渐变是支持的**。

### 关键启示
> **"不支持"和"用了但没效果"看起来一模一样。**
> 必须有一个**已知正确的对照组**，才能区分这两种情况。

## 方法 4：手动排除自动因素（用于"timer 是不是原因"）

### 适用场景
动画/定时器类问题，怀疑是触发机制的问题。

### 做法
**绕开 timer**，改成手动点击触发同一个状态变化。

### 当时的发现
呼吸动画不动 → 加"点击手动翻转"的对照 → **手动点击也不生效** → 排除 timer，锁定订阅问题。

### 关键启示
> **当"自动触发"和"手动触发"都不工作时，问题一定在"状态变化 → UI 更新"这条链路上**，与触发源无关。
> 这一步能把排查空间砍掉一半。

---

## 方法 5：源码追踪（用于"为什么行为与文档不符"）

### 适用场景
文档说支持，实际不生效。

### 做法
1. 找到对应的渲染层实现（`core-render-android`）；
2. 从 API 入口往下追到实际绘制/执行的地方；
3. **特别注意"计数器""标志位""临时修改后恢复"这类逻辑** —— 循环动画的问题几乎都在这里。

### 当时的发现
`repeatForever` 失效：
```kotlin
value.start(targetView) {
    animationRunningCount--      // 只有 onAnimationEnd 才减
}
animationRunningCount++          // 启动就 +1
// ...
if (v.isPlaying()) { v.cancelAnimation() }   // 每轮 attr 结束都调
```
**无限动画永不结束 → 计数恒 ≥1 → 每轮都被取消。**

### 关键启示
> **"文档说不支持"和"实现有 bug"是两回事。**
> 前者让你放弃，后者让你知道怎么绕。
> 追到源码才能区分。

## 方法 6：最小复现（用于"业务代码里查不出来"）

### 适用场景
在真实业务代码里试了多轮都不行。

### 做法
把这个功能抽到**一个独立的 `@Page`** 里，去掉所有业务逻辑，只留最小结构。

### 为什么有效
- 业务代码里有太多干扰因素（其他 observe、复杂布局、异步数据）；
- 独立页面里"能跑"还是"不能跑"是二元的，没有中间状态。

### 关键启示
> **当试到第 3 轮还不行，就该抽最小复现，而不是继续在业务代码里猜。**
> 继续猜的代价是：每轮 5-10 分钟，而且可能一路猜错方向。

## 方法 7：同源错误模式归纳

### 适用场景
同一个 bug 修好之后，怀疑它还有其他表现形式。

### 做法
问自己："**这个 bug 的根因是什么（不是现象是什么）？**"然后用根因去搜索代码。

### 当时的发现
`forEach` 渲染列表会空 → 归纳出根因 **"创建期读快照 = 断订阅"** → 发现还有两种表现：

| 现象 | 表面看起来 |
| --- | --- |
| `forEach` 渲染列表 | 面板能展开但空 |
| `forEachIndexed` 渲染动画 | **像动画坏了** |
| 把值算成 String 传给普通函数 | **代码完全正常，毫无破绽** |

### 关键启示
> **按"现象"记规则会漏，按"根因"记规则才能迁移。**
>
> ❌ "列表要用 vfor"（换个场景就不会触发）
> ✅ "创建期不能读快照"（任何场景都能触发）

## 排查顺序建议

```
1. 先量测，不要先猜     ← 有可量化的就量化
2. 能排除的先排除       ← A/B、手动对照
3. 有对照组再下结论     ← 防止"其实支持"被误判成"不支持"
4. 试 3 轮还不行 → 抽最小复现，不要在业务代码里继续猜
5. 修好后归纳根因 → 用根因搜同类问题
6. 追源码确认"为什么" → 写进文档，让别人不再踩
```

## 门禁：什么才算"查清了"

一个坑只有满足以下**全部**条件，才值得写进技能文档：

- [ ] 有**可复现的现象**描述（什么样的代码会出什么问题）
- [ ] 有**根因**（源码路径，或至少机制解释）
- [ ] 有**正确写法**（能直接抄的代码）
- [ ] 有**取证方式**（截图 / 采样数据 / 测试用例）

**没有做到以上四点的，标注为"未验证"，不要写成结论。**

> 宁可留一个诚实的缺口，不要一个漂亮的假象。
